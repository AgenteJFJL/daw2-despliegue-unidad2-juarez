1. Apache, MPM y módulos

Un servidor web recibe peticiones HTTP y devuelve páginas. Apache es el más usado en el curso. Piensa en él como un camarero: los MPM son la forma en que se organiza para atender mesas.

MPMCómo funcionaPara recordar
Prefork1 proceso por petición, sin hilosEstable, compatible con PHP clásico (no thread-safe), gasta más RAM
WorkerProcesos con varios hilosMás clientes con menos memoria
EventComo Worker, pero con un hilo para conexiones Keep-Alive inactivasEl recomendado hoy

Directivas de rendimiento

  • Timeout 60: segundos máximos esperando una petición o respuesta.
  • KeepAlive On: reutiliza la conexión para varias peticiones.
  • MaxKeepAliveRequests 100: peticiones máximas por conexión.
  • KeepAliveTimeout 5: segundos de espera de una nueva petición antes de cerrar.

Módulos: a2enmod / a2dismod

Activan o desactivan módulos creando o quitando enlaces simbólicos entre mods-available y mods-enabled (en /etc/apache2/). Después hay que reiniciar o recargar Apache.

MóduloPara qué
mod_rewriteReescribe URLs con expresiones regulares: URLs amigables, redirecciones, forzar HTTPS
mod_headersAñade cabeceras de seguridad (HSTS, CSP, X-Frame-Options)
mod_deflateComprime HTML/CSS/JS/JSON con Gzip (ahorra hasta ~70% de ancho de banda)
mod_proxy / proxy_httpProxy inverso hacia Node, Tomcat, Flask, Docker
mod_securityWAF: detecta inyección SQL, XSS, Path Traversal
mod_sslHabilita HTTPS

VirtualHost

Permite alojar varios sitios en la misma IP y puerto, distinguidos por el nombre (ServerName). Piezas clave: ServerName, ServerAlias, DocumentRoot (carpeta del sitio), ErrorLog, CustomLog ... combined. Se crea en sites-available y se activa con a2ensite. Para pruebas locales se añade el nombre en /etc/hosts (127.0.0.1 seguro.empresa.local).

Orden de procesado de directivas: <Directory> (de ruta más corta a más larga) → <Location> → .htaccess (solo si AllowOverride lo permite; se lee en cada petición).

Comandos útiles: apache2ctl configtest (valida sintaxis antes de recargar), systemctl reload|restart|status apache2.

2. Autenticación, control de acceso y hardening

Control por IP (Apache 2.4)

Require ip 192.168.1.0/24
Require ip 10.0.0.15
<FilesMatch "^\.(ht|git|env)"> Require all denied </FilesMatch>

Autenticación HTTP Basic

  1. Crear usuario: sudo htpasswd -c /etc/apache2/.htpasswd usuario (-c crea el fichero; sin él se añaden usuarios).
  2. Proteger la carpeta (en el VirtualHost o en .htaccess):
    AuthType Basic
AuthName "Zona restringida"
AuthUserFile /etc/apache2/.htpasswd
Require valid-user

Sin credenciales el servidor responde 401 Unauthorized. Basic envía la contraseña en Base64 (no cifrada), por eso conviene usarlo sobre HTTPS.

Hardening (bastionado)

Consiste en no regalar información a los atacantes. Se edita /etc/apache2/conf-available/security.conf:

DirectivaPor defectoRecomendadoEfecto
ServerTokensFullProdSolo muestra «Apache», sin versión ni SO
ServerSignatureOnOffQuita el pie con datos del servidor en páginas de error
OptionsIndexes FollowSymLinks-IndexesNo lista archivos si falta index.html
TraceEnableOnOffDesactiva TRACE (evita Cross-Site Tracing, XST)

Cómo se comprueba (curl -I)

  • curl -I http://sitio → cabecera Server: Apache sin versiones.
  • curl -X TRACE -I http://sitio → 405 Method Not Allowed.
  • curl -I http://sitio/admin/ → 401 Unauthorized.
  • curl -I http://sitio/viejo → 301 Moved Permanently hacia /nuevo/.

Redirección con mod_rewrite en .htaccess:

RewriteEngine On
RewriteRule ^viejo/?$ /nuevo/ [R=301,L]

R=301 = redirección permanente, L = última regla.

3. HTTPS, TLS y certificados

El problema: por HTTP (puerto 80) todo viaja en texto plano. Con tshark/Wireshark/tcpdump un atacante en la misma red lee usuario=admin&password=secreto123 (sniffing). HTTPS (puerto 443) cifra el tráfico con TLS.

PKI y certificados

El servidor presenta un certificado X.509 firmado por una CA (Autoridad de Certificación). Si el navegador confía en esa CA, no hay avisos.

  • Autofirmado (lo creas tú con OpenSSL): el navegador avisa porque no hay CA reconocida. Vale para desarrollo y pruebas. El error «self-signed certificate» no es un fallo de Apache ni de TLS.
  • De una CA (Let's Encrypt, DigiCert): válido sin advertencias.

OpenSSL: certificado autofirmado

sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
 -keyout apache-selfsigned.key -out apache-selfsigned.crt \
 -subj "/C=ES/ST=Madrid/O=Empresa/CN=localhost"

-x509 = certificado autofirmado; -nodes = clave privada sin contraseña (Apache arranca sin pedirla); -days 365 = un año; rsa:2048 = clave RSA de 2048 bits.

VirtualHost HTTPS (puerto 443)

<VirtualHost *:443>
 SSLEngine on
 SSLCertificateFile    /etc/letsencrypt/live/dominio/fullchain.pem
 SSLCertificateKeyFile /etc/letsencrypt/live/dominio/privkey.pem
 SSLProtocol all -SSLv3 -TLSv1 -TLSv1.1 +TLSv1.2 +TLSv1.3
 SSLCipherSuite HIGH:!aNULL:!MD5:!3DES
</VirtualHost>
<VirtualHost *:80>
 Redirect permanent / https://dominio/
</VirtualHost>

Se desactivan los protocolos obsoletos (SSLv3, TLS 1.0, TLS 1.1) y se dejan TLS 1.2 y 1.3. privkey.pem es la clave privada (nunca se comparte); fullchain.pem es el certificado más la cadena de la CA. Activar: a2enmod ssl headers, a2ensite default-ssl, configtest, reload. Verificar: curl -Iv https://localhost/ (con -k acepta autofirmados).

Let's Encrypt y Certbot

  • CA gratuita que usa el protocolo ACME; Certbot es el cliente que valida y renueva.
  • Instalación: apt install certbot python3-certbot-apache. Uso: sudo certbot --apache -d midominio.com -d www.midominio.com.
  • HTTP-01: Certbot deja un archivo en /.well-known/acme-challenge/ y Let's Encrypt lo pide por el puerto 80.
  • DNS-01: se crea un registro TXT en el DNS. Obligatorio para certificados wildcard (*.empresa.com).
  • Requiere dominio público y puertos 80/443 abiertos. Por eso en un laboratorio local se usa autofirmado.

Cabeceras de seguridad (con mod_headers)

CabeceraProtege de / hace
Strict-Transport-Security (HSTS)Obliga al navegador a usar solo HTTPS (ej. max-age=31536000)
X-Frame-Options SAMEORIGINClickjacking: impide incrustar la web en iframes externos
X-Content-Type-Options nosniffEvita que el navegador adivine tipos MIME
Content-Security-Policy (CSP)Limita desde dónde se cargan scripts, estilos e imágenes

Fallos típicos en una auditoría: HTTP sin cifrar, sin redirección a HTTPS, certificado caducado o autofirmado, TLS 1.0/1.1 o SSLv3, cifrados débiles, cadena de confianza rota, claves privadas mal guardadas.

4. Docker, proxy inverso y AWS EC2

  • Proxy inverso con SSL Termination: Nginx/Apache delante descifra el HTTPS y reenvía en claro, por la red interna de Docker, al contenedor de la app (Flask, Node, Django).
  • En docker-compose.yml: el proxy publica ports: "80:80","443:443"; el backend usa expose: "5000" (puerto solo interno); depends_on marca el orden de arranque; los volumes comparten certificados.
  • Security Group (cortafuegos de AWS): abrir solo 22 (SSH, idealmente solo tu IP), 80 y 443.
  • User Data: script que se ejecuta una vez al arrancar la instancia; instala y configura todo sin entrar por SSH.
  • Conexión: chmod 400 clave.pem y ssh -i clave.pem ubuntu@IP_PUBLICA.

5. Logs, GoAccess y Fail2ban

Logs de Apache

  • AccessLog: cada petición. Formato combined: IP, fecha/hora, método, URI, código de estado (200, 404, 500), tamaño, Referer y User-Agent.
  • ErrorLog: fallos y avisos; el detalle se regula con LogLevel (debug, info, warn, error, crit).
  • logrotate rota y comprime los logs de /var/log/apache2/ para no llenar el disco.

GoAccess (monitorizar)

Analiza el access.log y lo muestra como panel con estadísticas (hosts más activos, URLs, códigos de respuesta, tráfico), mucho más legible que leer el log a mano.

goaccess /var/log/apache2/access.log --log-format=COMBINED
goaccess access.log --log-format=COMBINED -o /var/www/html/monitor.html --real-time-html

-o = informe HTML de salida; --real-time-html = se actualiza en vivo. Se protege con <Location "/monitor.html"> + autenticación Basic, y se deja como servicio de systemd (goaccess.service, Restart=always, systemctl enable/start). Es normal ver IPs de bots y escáneres de Internet.

Fail2ban (prevenir)

Lee los logs, detecta patrones sospechosos (fuerza bruta, escaneos con muchos 404) y bloquea la IP añadiendo reglas a iptables/nftables. Se configura en /etc/fail2ban/jail.local:

[apache-404]
enabled = true
filter = apache-404
logpath = /var/log/apache2/access.log
maxretry = 10   # fallos permitidos
findtime = 300  # ventana de tiempo (s)
bantime  = 600  # duración del bloqueo (s)
  • El filter (/etc/fail2ban/filter.d/) define con failregex qué línea cuenta como fallo; <HOST> es la IP.
  • Comprobar: fail2ban-client status y fail2ban-client status apache-404 (muestra «Banned IP list»); también /var/log/fail2ban.log y iptables -L -n.
  • Simular ataque: for i in {1..20}; do curl http://IP/noexiste$i; done (genera errores 404).
  • Monitorización ≠ prevención: GoAccess observa, Fail2ban actúa. Un ataque de fuerza bruta prueba muchas combinaciones hasta acertar. Con maxretry=1 se bloquearía a la primera falta (riesgo de falsos positivos).
  • Limitación: un ataque distribuido desde muchas IPs, con pocas peticiones cada una, esquiva el bloqueo por IP. Otras medidas: WAF (mod_security), limitar peticiones, CDN, claves SSH en vez de contraseñas.
  • También protege SSH, FTP, correo, etc.
